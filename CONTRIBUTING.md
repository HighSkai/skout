# Contributing to Skout

Thanks for helping. The most useful contribution is a **false-positive report**: a line Skript accepts but Skout flags. Open an issue with the line, your Skript version and what `/sk reload` says. One report like that improves Skout for everyone.

## Getting started

You need Node.js 22 or newer, Git and VS Code.

```sh
git clone https://github.com/HighSkai/skout.git
cd skout
npm install
npm run build
```

Open the folder in VS Code and press <kbd>F5</kbd> (**Run Skout**). A second VS Code window opens with the extension loaded and `test-workspace/` open. Edit a `.sk` file there to see diagnostics. `npm run watch` rebuilds on every save.

## Project layout

```
client/src/       VS Code-only code: starts the language client
client/test/      integration tests that run inside a real VS Code
server/src/       the language server; never imports `vscode`
  parser/         line scanner, bracket checker, indentation tree
  skript/         ports of Skript's own rules: function signatures and calls, plurals, versions
  index/          per-file extraction (functions, calls, variables, options) and the workspace index
  syntax/         dump schema and importers, the bundled catalog, Skript's pattern compiler and matcher, the registry
  features/       LSP features (diagnostics, navigation, rename, outline, variables view, completion, syntax hover)
  upgrade/        the upgrade checker: workspace check, version diff, release-note changes, Markdown report
  engine/         the language engine: types, the recursive expression parser, line analysis, context checks
  environment/    the server folder: plugin jars, generated dumps, Skript's reload errors in the log
dumps/            bundled built-in syntax, normalized from Skript's docs.json (GPL-3.0)
server/test/      unit tests (vitest) and fixtures/*.sk
syntaxes/         TextMate grammar
test-workspace/   sample project the integration tests open
scripts/          build, corpus download and image rendering
```

The server must stay editor-agnostic. Anything that needs the VS Code API belongs in `client/`. [docs/architecture.md](docs/architecture.md) explains the layers and the decisions behind the engine.

## Tests

| Command | What it runs |
|---|---|
| `npm test` | Unit tests for the scanner, bracket checker and parser, plus a performance check |
| `npm run corpus` | Downloads Skript's own 587 scripts (pinned to 2.17.1) into `.corpus/`, after which `npm test` also parses all of them |
| `npm run test:integration` | Starts VS Code with the extension, opens `test-workspace/` and checks diagnostics, settings and the outline |
| `npm run typecheck` | TypeScript without emitting |
| `npm run sample-report` | Regenerates `docs/sample-upgrade-report.md` from the upgrade fixture |
| `npm run dumps` | Re-downloads Skript's docs.json for the bundled versions and rewrites `dumps/`, and regenerates the type names from Skript's `default.lang` (run when Skript releases) |

Run `npm run corpus` once before you change the parser or the index. The corpus test fails on any error Skout reports in a script Skript accepts, and runs the cross-file checks over Skript's test suite too.

`test:integration` uses your installed VS Code if it finds one (set `VSCODE_EXECUTABLE` to pick another) and otherwise downloads one.

## Rules for diagnostics

1. **Check Skript's source, never memory.** Every rule must trace back to Skript's code or documentation. Put a link or the class name in a comment, as `parser.ts` does for `SectionNode#load_i`.
2. **A false positive is worse than a miss.** If a check cannot be sure, it should stay quiet or lower its severity. `missing-colon`, for example, is only claimed for lines that can only be section headers.
3. **Upgrade rules come from data or release notes.** A behaviour change in `server/src/upgrade/known.ts` must link the release that announced it.
4. **Add a fixture.** Every new check needs a test with a line that triggers it and a realistic line that must not.
   Test addon syntax with made-up addons in the real formats (see `server/test/fixtures/dumps/`), never copies of real addon docs.
5. **Only report what is certain.** In the engine, a problem with any doubt (a part of the line Skout could not verify) is not reported. Unknown is not invalid: a span no known syntax explains is accepted everywhere.
6. **Keep it fast.** The performance test fails above 100 ms for a keystroke in a 2,000-line file (under 10 ms to re-parse and about 11 ms to type-check today) or above 1 s for the cross-file pass over 100,000 lines (about 40 ms).

## Pull requests

- One topic per pull request, with tests.
- `npm run typecheck`, `npm test` and `npm run test:integration` must pass.
- Describe user-visible changes in `CHANGELOG.md` under **Unreleased**.

## Releasing

1. Move the **Unreleased** notes in `CHANGELOG.md` under the new version and bump `version` in `package.json`.
2. `npm run package` builds `skout-<version>.vsix`.
3. Tag `v<version>` and attach the VSIX to a GitHub release.
