# Contributing to Skout

Thanks for helping. The most useful contribution is a **false-positive report**: a line Skript accepts but Skout flags. Open an issue with the line, your Skript version and what `/sk reload` says. One report like that improves Skout for everyone.

## Getting started

You need Node.js 22 or newer, Git and VS Code.

```sh
git clone https://github.com/HighSkai/skout.git
cd skout
npm install
npm run build
```

Open the folder in VS Code and press <kbd>F5</kbd> (**Run Skout**). A second VS Code window opens with the extension loaded and `test-workspace/` open. Edit a `.sk` file there to see diagnostics. `npm run watch` rebuilds on every save.

## Project layout

```
client/src/       VS Code-only code: starts the language client
client/test/      integration tests that run inside a real VS Code
server/src/       the language server; never imports `vscode`
  parser/         line scanner, bracket checker, indentation tree
  features/       LSP features built on the tree (diagnostics, outline)
server/test/      unit tests (vitest) and fixtures/*.sk
syntaxes/         TextMate grammar
test-workspace/   sample project the integration tests open
scripts/          build, corpus download and image rendering
```

The server must stay editor-agnostic. Anything that needs the VS Code API belongs in `client/`.

## Tests

| Command | What it runs |
|---|---|
| `npm test` | Unit tests for the scanner, bracket checker and parser, plus a performance check |
| `npm run corpus` | Downloads Skript's own 587 scripts (pinned to 2.17.1) into `.corpus/`, after which `npm test` also parses all of them |
| `npm run test:integration` | Starts VS Code with the extension, opens `test-workspace/` and checks diagnostics, settings and the outline |
| `npm run typecheck` | TypeScript without emitting |

Run `npm run corpus` once before you change the parser. The corpus test fails on any error Skout reports in a script Skript accepts.

`test:integration` uses your installed VS Code if it finds one (set `VSCODE_EXECUTABLE` to pick another) and otherwise downloads one.

## Rules for diagnostics

1. **Check Skript's source, never memory.** Every rule must trace back to Skript's code or documentation. Put a link or the class name in a comment, as `parser.ts` does for `SectionNode#load_i`.
2. **A false positive is worse than a miss.** If a check cannot be sure, it should stay quiet or lower its severity. `missing-colon`, for example, is only claimed for lines that can only be section headers.
3. **Add a fixture.** Every new check needs a test with a line that triggers it and a realistic line that must not.
4. **Keep it fast.** The performance test fails above 100 ms for a 2,000-line file. Today it is about 2 ms.

## Images

`images/icon.png`, `banner.png` and `diagnostics.png` are generated by `npm run images`. `diagnostics.png` is drawn from the parser's real output on `test-workspace/scripts/broken.sk`, so regenerate it when messages change.

## Pull requests

- One topic per pull request, with tests.
- `npm run typecheck`, `npm test` and `npm run test:integration` must pass.
- Describe user-visible changes in `CHANGELOG.md` under **Unreleased**.

## Releasing

1. Move the **Unreleased** notes in `CHANGELOG.md` under the new version and bump `version` in `package.json`.
2. `npm run package` builds `skout-<version>.vsix`.
3. Tag `v<version>` and attach the VSIX to a GitHub release.
